Install one small pod. ClusterSentinel watches your Deployments, StatefulSets, DaemonSets, Jobs, CronJobs, Pods and RBAC, checks them against 18 built-in rules (privileged containers, host namespaces, root users, `latest` tags, wildcard RBAC, cluster-admin bindings and more) and stores every issue as a `SecurityFinding` you can read with `kubectl`. It never changes your workloads: it tells you what to fix and how, and you decide.

> **Status: pre-alpha (Phase 1 of 7).** The operator runs, the CRDs install, and the RBAC, hardening and metrics endpoint are tested on kind. **It does not scan anything yet**: the rules engine arrives in Phase 2. Everything under [Features](#features) is the 0.1 target; [docs/implementation-plan.md](docs/implementation-plan.md) tracks what is done.

## Features

**Findings you can act on**
- 18 rules for containers, images, service accounts, RBAC and NetworkPolicy presence, each with an ID (`CS-CONTAINER-001`), a moderate default severity, evidence and a recommendation.
- One finding per workload, rule and container, never one per replica. Deleting and recreating a workload never inherits old findings.
- Findings move to `Resolved` by themselves when the issue disappears, and are cleaned up after a retention period.
- Profiles (`basic`, `recommended`, `strict`, `custom`) and per-rule overrides per namespace with a `SecurityPolicy`.

**Read-only, by design**
- `get`, `list` and `watch` on what it audits. It cannot create, patch or delete workloads, Pods, Secrets or RBAC objects, and it cannot read Secrets at all.
- Remediation is a YAML patch generated by the CLI for a human to review. Nothing is applied automatically.
- Runs as non-root with a read-only root filesystem, no capabilities, `RuntimeDefault` seccomp and no host access, so it passes the `restricted` Pod Security Standard.

**Light enough to forget about**
- Event-driven: a workload is analyzed when it changes, not on a polling loop. A periodic rescan (default 30 minutes, can be turned off) reads from the local cache, not the API server.
- The informer cache drops `managedFields`, `last-applied-configuration` and the specs of replica Pods. Secrets and ConfigMaps are never cached.
- One replica, no node agent, no database. Starting point: 25m CPU and 64Mi memory requested, 200m / 128Mi limits.

**Fits your existing tools**
- `kubectl get securityfindings -A` works out of the box.
- A `clustersentinel` CLI for summaries, reports (table, JSON, YAML), remediation patches and an optional CI gate.
- Notifications to Discord, Slack or any webhook, deduplicated and retried. Prometheus metrics with low-cardinality labels.

## Quick start

Requirements: Go 1.26+, Docker, [kind](https://kind.sigs.k8s.io/) and kubectl.

```bash
git clone https://github.com/rikyrism/clustersentinel.git
cd clustersentinel
make kind-deploy                          # local kind cluster, image built and loaded, operator deployed
export KUBECONFIG=$PWD/bin/kind-dev.kubeconfig
kubectl -n clustersentinel-system get pods
kubectl apply -k config/samples/          # example SecurityPolicy, SecurityFinding and SecurityReport
kubectl get securitypolicies,securityfindings -A
```

The kind targets write their own kubeconfig to `bin/` and never touch `~/.kube/config`, so they cannot reach any other cluster. `make kind-down` deletes the cluster.

### Development

| Command | What it does |
| --- | --- |
| `make test` | Unit tests and CRD validation tests against a real API server (envtest) |
| `make lint` | golangci-lint |
| `make test-e2e` | Creates a kind cluster, deploys the operator, checks readiness, hardening, metrics and RBAC, then deletes the cluster |

| `make manifests generate` | Regenerates CRDs, RBAC and deepcopy code after changing `api/` or RBAC markers |

## How it works

```
Kubernetes API ── watch (trimmed cache) ──▶ clustersentinel (one pod)
                                             ├─ Controllers: workloads, RBAC, namespaces
                                             ├─ Analyzer + rules engine ◀── SecurityPolicy, operator config
                                             ├─ Finding reconciler ──▶ SecurityFinding / SecurityReport CRDs
                                             ├─ Notifier ──▶ Discord · Slack · webhook
                                             └─ /metrics ──▶ Prometheus
kubectl / clustersentinel CLI ──▶ read SecurityFindings
```

- **CRDs are the source of truth.** No database: findings live in the cluster, have RBAC like any other resource and are deleted together with the workload they describe.
- **Templates, not replicas.** A Deployment with 50 replicas is analyzed once, from its pod template. Standalone Pods and Pods of controllers ClusterSentinel does not know are analyzed directly.
- **Deterministic identity.** A finding's name comes from the resource UID, rule ID and container, so a rescan updates it instead of creating a duplicate.
- **Writes only when something changed.** Unchanged templates are skipped, and `lastDetectedAt` is refreshed at most once per rescan.

Deeper notes: [implementation plan and architecture](docs/implementation-plan.md).

## Security model

- **What it reads:** workload specs, ServiceAccount, Role/ClusterRole and binding metadata, NetworkPolicy presence. Never Secret data, never environment variable values.
- **What it writes:** its own `SecurityFinding` and `SecurityReport` objects, and `SecurityPolicy` status. Nothing else. The ClusterRole is generated from [`internal/manager/rbac.go`](internal/manager/rbac.go) and verified by the e2e tests with `kubectl auth can-i`.
- **Notification secrets:** webhook URLs stay in Secrets in the operator's namespace, granted by name. They are never logged or copied into CRDs.

> ClusterSentinel assesses configuration. A clean report does not mean a cluster is secure: it does not scan images, detect runtime threats or prove that network traffic is restricted. Use it alongside tools such as Trivy, Falco or Kyverno, not instead of them.

## Resources it creates

| Kind | Short name | What it holds |
| --- | --- | --- |
| `SecurityPolicy` | `secpol` | Profile and per-rule overrides for one namespace (written by you) |
| `SecurityFinding` | `secf` | One issue: rule, severity, resource, container, evidence, recommendation, Open/Resolved |
| `SecurityReport` | `secr` | One cluster-wide summary: counts per severity, last scan, scanner health |

```yaml
apiVersion: security.clustersentinel.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: production-baseline
  namespace: app
spec:
  profile: recommended
  rules:
    runAsRoot: { severity: HIGH }
    missingNetworkPolicy: { enabled: true }
```

## Project structure

```
api/v1alpha1/          CRD types: SecurityPolicy, SecurityFinding, SecurityReport (+ schema tests)
cmd/                   Operator entrypoint (manager)
internal/config/       Operator configuration (from Helm values), validation
internal/manager/      Cache trimming, memory limit, RBAC contract
internal/rules/        Rule catalog: IDs, keys, default severities, profiles
config/                Kustomize manifests: CRDs, RBAC, manager, samples
hack/                  kind cluster config, development config
test/e2e/              End-to-end tests on kind
docs/                  Implementation plan, architecture, assets
```

## Roadmap

1. ~~Bootstrap: CRDs, manager, Dockerfile, kind workflow, RBAC contract~~ (done)
2. Workload scanning: controllers, analyzer, the 18 rules
3. Findings: reconciliation, deduplication, resolution, retention
4. Configuration: profiles, overrides, namespace filtering
5. CLI: `summary`, `findings`, `describe`, `report`, `fix`, `rules`, CI gate
6. Notifications (Discord, Slack, webhook) and Prometheus metrics
7. Helm chart, CI/CD with image and dependency scanning, full documentation

## Limitations

- Pre-alpha: no rule is evaluated yet, and the CLI and Helm chart do not exist yet.
- Not tested on a managed cluster (EKS, GKE, AKS) yet, only on kind and envtest.
- The NetworkPolicy rule only checks whether a namespace has any NetworkPolicy. It is a hint, not proof that traffic is or is not restricted.
- Resource figures are targets until they are measured on a large cluster.
